# 书屿 · 共享图书借阅平台

> **BookLoop** — 共享借阅 · 押金担保 · 到馆核销 · 在线支付

面向中小型共享书架 / 图书角的借阅流通系统。用户**免费借阅**，借书时缴纳与书价等额的**押金**，按期归还后原路全额退还；逾期从押金中扣除，逾期满约定期限视为购买。也可直接购买图书。

技术栈：**Spring Boot 2.7 + MyBatis-Plus + MySQL 8 + Vue 3 + Element Plus + 支付宝开放平台**

---

## 一、这个项目解决什么问题

共享书架最大的痛点是**书一旦借出去就收不回来**。不收钱，用户没有归还动力；收租金，又不符合"共享"的定位。

本项目的答案是**押金制**：

- 借书时缴纳等值于书价的押金，钱在平台手上，用户有归还动力
- 按期归还全额退还，用户没有额外负担
- 逾期按天扣押金，扣光或逾期满 30 天视为购买
- 最坏情况是"完成了一笔销售"，平台不会出现坏账

## 二、为什么不用「余额充值 + 扣款」

第一版做的是预存余额，写完发现一个结构性缺陷：**用户账户没钱时，逾期扣款会失败**。此时书已经在用户手上，平台既收不到钱、也要不回书，只能把用户拉黑——而对一个陌生用户，拉黑毫无约束力。

押金制从根上解决了这个问题：**钱在下单时就已经在平台手上**。因此 2.0 直接删掉了余额模型（`user.balance` 字段已从代码和数据库中移除），改为"一单一押金、归还即退款"。

## 三、四个关键设计

### 1. 副本级建模：ISBN 标识「一种书」，条码标识「一本书」

馆藏 3 册《三体》，ISBN 完全相同。若按 ISBN 核销，管理员扫一下只知道"这是《三体》"，**不知道扫的是第几册**——而第 2 册正在别人手上。

因此拆成两层：

```
book（书目）  1 ──── N  book_item（副本，每册独立条码 B001001）
```

`book.stock` 不再是业务字段，只是 `book_item` 在馆数量的统计缓存。

### 2. 到馆核销：借期从扫码那一刻起算

线上点击不能代表物理动作。用户点「归还」时书可能还在他手上，此时把库存 +1，别人就能借走一本根本不存在的书。

所以借还都必须到馆由管理员**扫描副本条码**完成核销，且借期从核销时刻起算，而不是下单时刻。

借出核销要过 5 项校验，其中最关键的一条是**「该读者确实有待取书单，且预定的就是这一册」**——没有这一步，任何人拿任何一本书都能核销成功。

### 3. 预留机制：防止多人抢同一册

用户 A 和 B 都付了押金、都处于「待取书」，但馆里只有 1 册，谁先来谁拿到，另一个人的押金就悬空了。

解法是下单时就把副本状态从「在馆」原子切换为「已预留」，两人的条件更新只有一个能成功。超时未取则释放回「在馆」并自动退款。

### 4. 支付幂等：靠 SQL 条件更新，不靠 if 判断

回调会被重复推送，查单补偿也可能和回调撞车。`if (order.getStatus() == 0)` 是无效的——两个线程会同时读到 0。

正确做法是把判断写进 SQL：

```sql
UPDATE pay_order SET status = 1, trade_no = ?, pay_time = ?
WHERE order_no = ? AND status = 0
```

影响行数为 1 才继续入账，为 0 说明已被处理，直接返回成功。

同理，退款的累计金额也由 SQL 卡死：

```sql
UPDATE pay_order SET refund_amount = refund_amount + ?, status = IF(...)
WHERE order_no = ? AND refund_amount + ? <= amount
```

超退直接 0 行，不依赖应用层校验。

## 四、功能

**读者端**
- 浏览 / 搜索图书，查看在馆状态
- 申请借阅 → 支付押金 → 到馆取书
- 我的借阅：状态、条码、押金、剩余天数、押金结算明细
- 取消未取书的借阅（全额退押金）
- 图书预约排队（FIFO，有书归还后按顺序通知）
- 直接购买图书
- 借阅规则强制确认（首次弹窗 + 版本留痕）
- **消息中心**：到期提醒、逾期提醒、预约到书通知，侧栏未读角标

**管理端**
- 书目管理（**支持扫码/输入 ISBN 自动回填书名、作者、封面**）、副本管理（自动生成条码、标记遗失/破损/下架）
- **借出核销 / 归还核销**（扫码枪回车即提交，自动结算逾期费与破损赔偿）
- 借阅记录、订单管理、读者管理、预约管理、公告、数据统计
- **资金对账**：每日自动拉取渠道账单逐笔核对，差异人工处理
- **操作日志**：核销、扣款、禁用账号等敏感操作全量留痕（含失败尝试与入参）

## 八、快速开始

### 1. 初始化数据库

```bash
mysql -uroot -p < sql/init.sql
# 增量脚本（站内信 / 操作日志 / 对账 / ISBN 缓存 / 退款滞留字段）
# 脚本刻意不写死库名：用哪个库就在命令里指定，主库和测试库共用同一份；均可重复执行
mysql -uroot -p library < sql/patch-2026-11-04-v3.sql
mysql -uroot -p library < sql/patch-2026-11-04-v4.sql
```

会创建 `library` 库、全部表、管理员与示例读者、10 种图书，并按各书目的 `stock` 自动生成副本（当前初始化数据共 **44 册**；`stock=0` 的《三体》不生成副本，用于演示预约排队）。

### 2. 启动后端

```bash
cd backend
mvn clean package -DskipTests
java -jar target/library-management-1.0.0.jar
```

或直接双击根目录的 `start-backend.bat`（已内置 JDK 路径，端口 8080）。

### 3. 启动前端

```bash
cd frontend
npm install
npm run dev
```

或双击 `start-frontend.bat`，访问 `http://localhost:5173`。

### 4. 配置支付

支付参数在 `backend/src/main/resources/application.yml` 的 `library.pay.alipay` 下。应用私钥放在 `backend/src/main/resources/certs/app_private_key.txt`（已在 `.gitignore` 中排除，不会提交）。

沙箱与正式环境只差 5 个配置项：`app-id`、`gateway-url`、应用私钥、支付宝公钥、`notify-url`。**业务代码零改动。**

> `notify-url` 必须是公网可达地址，本地调试可用内网穿透（如 natapp）。回调丢失时系统会通过定时查单补偿自动补入账。

## 十、已知边界

诚实地说，这个系统有几件事做不到，也不打算假装能做到：

1. **无法校验物理动作**。核销依赖管理员扫码，如果管理员失真操作，系统无法察觉。
2. **押金不是真正的资金冻结**。支付宝的资金预授权产品仅对企业主体开放，个人只能用"收款 + 退款"模拟，押金实际会先进平台账户。
3. **只支持 PC 端支付**。签约的是「电脑网站支付」，手机浏览器访问会提示使用电脑。
4. **对账依赖账单接口权限**。真实对账需要开放平台的账单下载权限；拿不到账单时会退化为
   「用本地数据构造渠道侧」的模拟对账，只能验证比对链路，不能验证真实差异。
   **判断是否真的在对账，看返回里的 `simulated` 字段**：`true` 表示这一轮是空转的，
   页面上就算显示「无差异」也不代表账没问题。
   另外账单包有几处容易踩的细节，都有专门的解析测试兜底：
   条目名是 GBK（不是 UTF-8）、文件名是中文的（`业务明细.csv`，不含 `trade`）、
   列名带单位后缀（`支付宝交易号`、`订单金额（元）`）、解析 CSV 时不能关闭底层流
   （`BufferedReader.close()` 会连带关掉 `ZipInputStream`，导致后续 `getNextEntry()` 报 Stream closed）。
   <br>还有一层保护：**渠道账单为空而本地有已支付单时，不写入差异表**，只提示「本次未做差异判定」——
   沙箱不把交易写进正式账单，这时把每笔都报成「疑似伪造回调」纯属误导。
5. **定时任务按单机设计**。多实例部署时逾期处理、提醒生成会被多个节点各跑一遍——业务写操作都有条件更新兜底，不会产生重复数据，但会多打几次库。真要横向扩展需要引入分布式锁。
6. **对账只逐笔覆盖收款侧**。退款没有做渠道账单逐笔比对：退款失败先由补偿任务重试，
   超过 24 小时（由 `refund_fail_time` 起算）仍未成功则在对账页报一条「退款滞留」。
   要真正比对退款明细，需要额外解析 `bill_type=refund` 的账单，
   而沙箱环境拿不到该数据，无法验证的代码不如不写。

这些边界在 `docs/` 的设计文档里有更详细的说明。

## 十一、质量保障

### 并发与幂等测试

核心不变量只有几条 SQL 条件更新，光靠点页面永远验证不到竞态。测试用真实 MySQL 并发打一遍：

```bash
# 一次性准备测试库（不会影响 library 开发库）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS library_test DEFAULT CHARACTER SET utf8mb4"
mysql -uroot -p library_test < sql/init.sql        # 需先把库名改成 library_test
mysql -uroot -p library_test < sql/patch-2026-11-04-v3.sql

# 运行（surefire 默认跳过 @Tag("it")，-Pit 才会执行）
cd backend && mvn test -Pit -Dtest=ConcurrencyIdempotencyTest
```

覆盖的七个场景：

| 用例 | 验证的不变量 |
|---|---|
| 两人同抢仅剩 1 册 | 副本状态机条件更新，只有一人抢到 |
| 支付回调并发 10 次 | `markPaid` 的 `status=0` 闸门，只入账一次、流水只多一条 |
| 退款补偿重复触发 | 退款流水表做最终幂等，累计退款金额不翻倍 |
| 支付后超时未取书 | 按 `pay_time` 判定超时，释放副本并唤醒预约队列 |
| 逾期费超过押金 | 提前买断，不等满 30 天 |
| 已退款订单对账 | 模拟对账的渠道侧与本地侧口径一致，不产生假差异 |
| 退款滞留 | 补偿持续失败超过阈值会被报出；合并单下每笔独立成条，计时用 `refund_fail_time` 而非 `update_time` |

完整执行（含单测，共 22 个用例）：

```bash
mvn test -Pit
```

### 审计日志脱敏

审计日志是只追加、不修改的，一旦写进明文密码就再也删不掉。所以脱敏做在切面里，
不依赖调用方记得加 `recordArgs = false`：

- 字段名命中 `password / pwd / token / secret / privateKey` 的一律替换成 `***`，嵌套结构与数组递归处理
- **入参照常记录**：脱敏后的日志仍保留「操作了哪个 id、改了哪些字段」，落库效果 `[2,{"password":"***"}]`。
  整条关掉入参虽然也能防泄露，但等于放弃了审计的可追溯性——安全不等于失明
- `LogParamMaskerTest` 覆盖顶层、大小写变体、嵌套结构、空入参、目标 id 保留五类情况，默认 `mvn test` 就会执行
- 已知边界：脱敏按**字段名**匹配。如果新增的审计接口把密码作为裸字符串参数传（不在对象里），不会被掩码，这类接口应显式设 `recordArgs = false`

### 一次真实踩到的坑

`PayServiceImpl.doPaid()` 原本是同类方法内部调用，`@Transactional` 被 Spring 代理机制静默忽略——回调路径因为外层有事务没暴露，**查单补偿路径实际是无事务的**。抽成独立 Bean `PaySettleHandler` 后才真正生效。这类问题只有写测试或做代码审查才能发现。
